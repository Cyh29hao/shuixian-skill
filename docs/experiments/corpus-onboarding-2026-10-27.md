# 从自己的语料到水仙：2026-10-27 实操

这次检查的是“导入选好的本人语料，整理说话方式，保存镜像并开始对话”，同时检查 Codex / Claude Code 的安装文件和工具路径。材料全部是公开自编合成数据，没有读取真实微信账户。

## 12,000 条消息：工具处理与模型阅读分开

- 合成 JSON 共 12,000 条，青禾（本人标签）和阿遥各 6,000 条，源文件约 1.87 MB。
- 实际运行 `transcript_importer.py`，再运行 `mirror_profiler.py --self-name 青禾`，画像报告识别出本人 6,000 条。输入字节校验前后相同。
- agent 依据本人样本准备语气、思路、关系和元数据，用 `skill_writer.py create` 实际保存，随后 `list` 回读。
- 导入、画像、保存、列表这四次本地 CLI 合计 **3.55 秒**。不包含下载、微信取数、模型分析、用户决定或宿主刷新，不能宣传为完整上手耗时。

本人语料只有8种模板，对方只有4种，另有少量对象替换与不同时间戳。它适合检查规模处理和说话人归属，不代表真实大量记录的语言多样性。该 agent 使用自己编写的模板及统计结果合成配置，没有逐条用模型阅读12,000条；writer也不是自动训练人格的程序。

## 保存后，实际接了两轮话

原生 agent 读取保存后的 `SKILL.md`、`style.md`、`mind.md`、`relationship.md` 后实际作答。测试输入是合成场景：

> 刚把乱七八糟的表格整理完，文件名还叫“最终版真的最终版7”。

实际回复：

> 第七个最终版，终于轮到它下班了。先别开第八个，得意两分钟。

这句短、具体，但套用了样本里的庆祝说法，还多给了安排。因此继续纠正：

> 别每次都让我得意两分钟，这次就吐槽文件名，别安排我下一步。

实际回复：

> 这文件名已经把自己说急眼了：最终，真的，信我，第七次。

第二轮收回了安排和庆祝套话。这是当前对话纠正，没有永久保存，也不证明真人相似度或长期稳定性。同一个 agent 编写样本、配置和试聊，因此这部分不是独立盲测。

## 陌生 agent 从候选技能开始的一次上手

另外启动一个没有继承前面实验过程的原生 agent，只给当前候选技能目录、指定合成导出、本人名称、只保存抽象语气的要求，以及“整理文件却整理出三个新建文件夹”的话题。它不读取前面实验的角色规则、模板脚本或报告。

它把当前85个产品文件安装到一个新的隔离 Codex 项目，导入12,000条并确认本人6,000条。实际分四批读了36条本人发言与36条相邻对方发言，其中本人有32条不同文本；这是有限阅读，不是全量模型理解。原先给的导出文件名不正确，它只检查指定目录，找到唯一合成JSON后核对了发言者，没有扫描私人目录。

它依据这些语句创建并读回 `shuixian-echo-one`，命令实际同时提示 Codex 的 `$shuixian-echo-one` 和 Claude Code 的 `/shuixian-echo-one`。随后原生 agent 对给定话题实际回复：

> 文件还没归位，安置房先盖了三套。先别盖第四套了。

这说明候选技能能引导另一个 agent 完成指定可读语料的安装、整理、创建和一次接话；仍是合成语料、显式读角色文件，不是 Codex 主宿主自动发现，也不是 Claude 运行验收。安装来源是本轮工作树副本，远程网络 clone 的验证另见下节。回复仍可继续校准，例如用户是否喜欢末尾那句安排，需要真实使用来判断。

## 两宿主的手动安装

采用官方目录与 `git clone`，不另建安装器：

| 项目宿主 | 安装目录 | 构建器调用 |
| --- | --- | --- |
| Codex | `.agents/skills/create-shuixian` | `$create-shuixian` |
| Claude Code | `.claude/skills/create-shuixian` | `/create-shuixian` |

在两个带中文、空格的隔离项目中，分别从公开 GitHub 仓库实际克隆了 `56722ee`，各核对78个资源文件。随后从安装副本运行预设列表、6条公开JSON导入、本人3条画像、镜像生成、整节纠偏、镜像列表和版本列表；原始语料、builder资源、未修改的配置节保持不变。再次 clone 被 Git 拒绝，原文件保留。

共20条捕获的子进程命令，包含两次按预期拒绝的重复clone；命令执行合计约24.97秒。这里只测下载与文件/工具集成，不是完整agent上线耗时。初次验收脚本错把报告的两个计数字段当成“3/6”字符串，修正检查后复用了已成功产物，没有改产品来迎合检查。

本会话 PATH 未找到 `claude`，没有启动真实 Claude Code。这些结果不能替代 Claude 主机发现、模型接话或实际用户体验。新工作树另修正了 builder 的宿主路径指引及 CLI 输出：同时给出 Codex `$` 和 Claude `/` 调用名，不再让 Claude 用户照着 Codex 提示操作。

官方依据：[Codex skills](https://learn.chatgpt.com/docs/build-skills)、[Claude Code skills](https://code.claude.com/docs/en/skills)。本轮实际打开并核对了目录、调用名与刷新方式。

## 微信原始数据库仍有缺口

自编旧式明文 `MicroMsg.db` / `MSG0.db`、`Contact` / `MSG` 表，20条消息提取成功，本人10条，源数据库字节未改。另一份只使用 `contact.db` / `message_0.db` 文件名的空库被当前发现逻辑拒绝；这不等于复现了完整微信4.x。

没有在真实微信客户端取钥或解密。旧解密器的 `test_key` 判断不足以可靠验证密钥，本机也缺少其加密依赖；本轮未安装或运行它。因而不能用一句“best effort”暗示任意本机微信几分钟直达。[当前微信路径与限制](../../references/wechat-import.md)。

## 还不能据此宣称

- 任意本地微信版本都能自动导出，或完整流程固定几分钟。
- 文件安装等于新宿主已发现；两宿主目录通过等于真实 Claude 试聊通过。
- 消息全量机械处理等于模型全量阅读，更不等于已还原真人。
- 一次改口等于已经永久保存，短试聊等于长期效果。

结论是：可读语料的安装、整理和保存路径已实操；“像不像自己”仍要由真实材料与实际对话来校准。
