# 先弄清楚，哪几句是我说的

2026-10-26。一次公开合成的导入实操：六条消息，青禾和阿遥各说三条。青禾喜欢短句、轻调侃，阿遥偏好长篇安慰；这里的名字和内容均为实验夹具，没有导入私人聊天。

## 第一次：命令成功，但还没认出自己

先用现有转录导入器读取 JSON，六条消息及两人的标签保留下来。随后运行画像工具，没有指定自己的名字。

画像命令退出成功，却显示 `Identified user messages: 0/6`。标准错误和报告正文提示补上 `--self-name`；报告没有拿阿遥的发言当作用户特征。文件生成了，不等于已经认对了说话人。

## 第二次：把导出中的名字告诉它

在同一次导入的文本上，加 `--self-name "青禾"` 再运行。实际输出变为 `Identified user messages: 3/6`。报告的用户线索来自青禾，没有引用阿遥的长篇鸡汤；原始 JSON 的字节和哈希保持不变。

所以[上手命令](../quickstart.md#4-导入已有聊天先选范围和说话人)现在直接带这个参数，并提醒替换成自己的标签、先看转录、再核对人数。不用先读完整命令帮助，才发现自己没有被识别。

## 画像还会漏什么、误读什么

实操中，“我喜欢短句。先说重点，哈哈。”被归入了 `love-and-relationship`。原来的关键词包含单独的“喜欢”和“爱”，把普通表达偏好也当成恋爱话题。工具现已收窄为较明确的关系词，并用普通偏好与明确恋爱话题做回归；不增加新的语义模型。

“轻调侃”没有被报告明确提取出来。它仍是关键词和统计整理器，不是完整的偏好理解器；这次没有为了报告看起来更齐全而扩充一套人格分类。把这句原话连同来源给 builder，仍然有用。

这些检查没有证明任意平台导出都兼容、关系推断准确，或生成的水仙像本人。导入、说话者识别、画像线索和实际试聊要分别看。

随后用含中文和表情的路径继续实操，复现了 Windows 旧编码管道下转录、画像和素材归档三个入口的输出失败。现在这三处入口与已有创建工具一样，明确输出 UTF-8；真实子进程检查确认命令成功、路径可读、原材料不变。4 项 CLI 编码检查与 29 项导入检查通过；这不表示所有渠道工具都已覆盖。
